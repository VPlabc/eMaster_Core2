Lua API Reference

Rest

Rest.SetUrl(url)

Sets the base server URL used by Rest.Get / Rest.PostForm. Rest.SetServer(url) is an alias for this — same function, either name.

Parameters: url (string)

Return: none

Example:

Rest.SetUrl("http://0.0.0.0:8090")
-- or, identically:
Rest.SetServer("http://0.0.0.0:8090")
Rest.SetApiKey(key)

Sets the API-Key header value sent with every request.

Parameters: key (string)

Return: none

Rest.PostForm([path,] data)

Sends data as multipart/form-data, retrying up to the configured retry count. With one argument, posts to the server URL set via Rest.SetUrl/Rest.SetServer as-is. With two, path is joined onto that server URL (e.g. server http://0.0.0.0:8090 + path /api/citizen/verify) — handy when posting to different endpoints on the same server without calling Rest.SetUrl before every request.

Parameters: path (string, optional), data (table of string => string)

Return: a table: ok (boolean), status (integer), body (string, raw response body). If the response body is a JSON object, its top-level fields are merged into this same table — a server reply like {"success":true,"message":"OK"} is readable directly as result.success / result.message, no separate JSON decoding needed.

Example:

local result = Rest.PostForm("/api/citizen/verify", { card = cardJson })
if result.success then
  Log.Info("verified")
else
  Log.Error(result.message or "verify failed, status " .. tostring(result.status))
end
Rest.Get([pathOrUrl])

Performs an HTTP GET. The optional argument is either a full URL (used as-is, if it contains ://) or a path joined onto the configured server URL, same as Rest.PostForm's path argument. Omit it to GET the configured server URL directly.

Parameters: pathOrUrl (string, optional)

Return: same table shape as Rest.PostForm: ok, status, body, plus any top-level JSON object fields from the response merged in.

Serial

C++ owns the port, not your script. The gateway opens both serial ports at startup and keeps them open, with a background worker that reopens either one if it drops (1 s / 2 s / 5 s backoff). A script never has to manage the hardware, and never waits on a reconnect: reads simply return nil while a port is down. See docs/FixSerial.md.

So the old pattern is now wasteful rather than necessary:

-- Don't: pays an open/close cycle every iteration
while true do
  Serial.Open()
  local data = Serial.Read()
  Serial.Close()
  Sleep(100)
end

-- Do: the port is already open
while true do
  local data = Serial.Read()
  if data then ProcessSerialData(data) end
  Sleep(100)
end
Serial.Open()

Opens the serial port using the currently configured settings (port, baud rate, parity, stop/data bits). Idempotent: calling it on a port that is already open with the same settings does nothing and returns true immediately — it does not close and reopen. Only a changed port or changed settings cause a real reopen.

When the port cannot be opened, a background worker keeps retrying, so a reader that is plugged in later comes up on its own without the script calling Serial.Open() again.

Return: ok (boolean) — whether the port is open now

Serial.Close() · Serial.Release()

Does not close the hardware. It releases your script's claim on the port; the physical port stays open and keeps receiving. The two names are the same function.

This is deliberate: the reader is permanently attached and the gateway is its only user, so a script that closed the port between polls was paying a full open/close cycle per iteration — which is what made the workflow stall for seconds at a time. Existing scripts that call Serial.Close() keep working; the call is now just cheap.

Return: none

Serial.Shutdown()

Actually closes the physical port and stops its worker (including any reconnect attempts). For handing the device to another program, or a deliberate teardown — not for use in a polling loop.

Return: none

Serial.IsOpen()

Return: bool — whether the port is open right now.

Serial.Status()

Connection state as a string: OPEN, CLOSED, RECONNECTING (configured, worker retrying in the background) or ERROR (open failed and auto-reconnect is off).

Return: string

Example:

if Serial.Status() ~= "OPEN" then
  Log.Warning("Card reader offline: " .. Serial.Status())
end
Serial.Read()

Returns all raw bytes received since the last call to Serial.Read(), or nil if none arrived. No line-splitting or other framing is applied — this returns exactly what the device sent, whole and unmodified, including any embedded \r/\n/\0 bytes that are part of the payload rather than a delimiter. If your device frames messages with a real delimiter or fixed length, do that parsing in the script.

Return: data (string or nil)

Serial.Write(text)

Writes raw text to the serial port.

Parameters: text (string)

Return: ok (boolean)

Serial2

A second, fully independent serial port, configured under serial2 on the Configuration page. It drives the TDM-800 LED display (see request/LEDBoard.md); scripts normally use require("led") rather than these directly, since led.lua owns the frame format. Same four calls as Serial above, with two differences worth knowing:

  • Serial2.Write is binary-safe: LED frames start with a 0x00 command byte and end with 0x0D, so the whole string is written by length rather than stopping at the first null.
  • Serial2.Read does not deliver queued events the way Serial.Read does — that behaviour exists for scripts polling the citizen reader, and this port isn't that.

It has the same full set of calls and the same lifecycle rules as Serial above, on its own independent port, worker and buffers: Open (idempotent), Close/Release (releases the claim, port stays open), Shutdown (really closes), Read, Write, IsOpen and Status. Neither port can block or interfere with the other.

Serial2.Open()

Opens the port using the serial2 settings from the Configuration page.

Return: ok (boolean)

Serial2.Close()

Return: none

Serial2.Read()

Raw bytes received since the last call, or nil. No framing applied.

Return: data (string or nil)

Serial2.Write(data)

Writes data verbatim, embedded null bytes included.

Parameters: data (string)

Return: ok (boolean)

Example: prefer the led module, which owns the frame format:

local Led = require("led")
Led.Show("Moi quet CCCD")

Rfid

The reader's Method is chosen on the Configuration page, and decides both where card reads come from and what "connected" means:

  • TCP JSON payload — the gateway connects to a TCP server that sends one JSON object per read and takes the value from data.Raw. Connected = that session is up.
  • ZK protocol — a ZKTeco controller over PullSDK, with its own heartbeat and auto-reconnect. Connected = that controller link. Cards also reach scripts through require("zk_controller") below.
  • Card Reader Client API — readers POST to /api/card/input, so there is no outbound connection; connected = the reader answers a ping. Cards arrive via Card.*.
Rfid.IsConnected()

Reports the current state of whichever method is configured. The gateway owns the connection and its retry loop independently of the script — this only reports state, it doesn't connect or disconnect anything.

Return: bool

Example:

if Rfid.IsConnected() then
  Log.Info("RFID Connected")
else
  Log.Error("RFID Disconnected")
end

Reports whether the gateway currently has a live Modbus TCP connection to the PLC. Doesn't attempt to connect or reconnect itself — the gateway manages that connection independently of the script.

Return: bool

Example:

if Modbus.IsConnected() then
  Log.Info("PLC Connected")
else
  Log.Error("PLC Disconnected")
end
Modbus.CheckConnect(ip, port)

One-shot connectivity check against a PLC at an explicit IP/port — opens a temporary connection, tests it, then closes it again. Independent of the gateway's own configured PLC connection, so it can be used to probe a different PLC without touching the live connection Modbus.IsConnected() reports on.

Parameters: ip (string), port (integer)

Return: ok (boolean)

Example:

if Modbus.CheckConnect("192.168.2.203", 502) then
  Log.Info("PLC reachable")
else
  Log.Error("PLC not reachable")
end

Modbus.ReadDiscreteInput(address) / Modbus.ReadDiscreteInput(ip, port, address)

Alias: Modbus.ReadDiscInput(...) — identical function, for the shorter spelling most PLC tooling uses.

Reads a discrete input (function code 0x02). This is a different, read-only address space from coils — most PLCs map their physical input terminals here, and answer a Modbus.ReadCoil of the same address with an exception or with unrelated data. If an input reads as nil or is stuck, this is usually the reason.

One argument uses the gateway's configured PLC connection; three open a one-shot connection to an explicit address, same as Modbus.ReadCoil.

Return: bool, or nil on error

Example:

-- sensor wired to a physical input terminal
if Modbus.ReadDiscInput(1024) then
  Log.Info("card taken")
end
Modbus.ReadDiscreteInputs(address, count)

Alias: Modbus.ReadDiscInputs(address, count)

Block read of consecutive discrete inputs from the configured PLC connection.

Return: table of booleans, or nil on error

When a read returns nil

A nil return means the read failed, not that the value is off. The reason is written to the Modbus log — the common ones being:

  • Modbus exception 0x2 (illegal data address) — the PLC answered, but has nothing at that address. The link is healthy; the address is wrong. Vendors base their I/O at wildly different offsets (0, 1, 1024, 8192, 10000…), so check the vendor's address map, or run io_test.lua, which scans common bases and reports which ones this PLC accepts.
  • Modbus exception 0x1 (illegal function) — the PLC does not implement that function code at all; e.g. it has no discrete-input space and maps everything to coils.
  • no response (timeout) / send failed — a genuine transport problem. Three of these in a row mark the PLC disconnected so auto-reconnect takes over. Exceptions do not count toward that, since a device that answers is plainly alive.
Modbus.RegisterInput(name, address [, source]) / Modbus.RegisterOutput(name, address)

Attaches a display name to a coil so the Dashboard's PLC Input / PLC Output panels can show labelled I/O instead of bare addresses. Declaration only — these do not read or write anything; the gateway polls the registered addresses itself and pushes the values over the WebSocket.

Registered outputs also become manually testable from the Dashboard (Admin only). The toggle resolves the coil by name through this registry, so only points a script deliberately registered can be driven. Outputs are always coils (FC01) — there is no writable discrete-input space.

Parameters: name (string), address (integer coil address), source (optional string, inputs only)

source selects the address space an input is read from:

  • "auto" (default) — try discrete inputs (FC02), fall back to coils (FC01) if the PLC rejects FC02. The point latches onto whichever answered.
  • "discrete" (or "fc02") — always FC02.
  • "coil" (or "fc01") — always FC01.
If a PLC input never changes, this is almost always why. Coils and discrete inputs are separate address spaces, and many PLCs answer both function codes at the same address while only one carries the live state — the other returns a constant. Because both replies are valid, "auto" cannot detect the difference: it picks FC02 and the dashboard row sits at OFF forever. Each input row on the Dashboard shows the function code that produced its value (FC01 / FC02); if that row is frozen, register it with the other space. The io_test.lua script registers both spaces side by side to make the comparison directly.

Return: none. An unrecognised source raises an error rather than silently polling the wrong space.

Registrations belong to the runtime that made them: re-running or stopping a script clears its points and leaves every other running script's alone. Call these at the top level of a module that gets loaded on every run. Re-registering an existing name updates its address rather than adding a duplicate.

Example:

Modbus.RegisterInput("Card Taken", 1024, "coil")      -- FC01
Modbus.RegisterInput("Door Sensor", 1025, "discrete") -- FC02
Modbus.RegisterInput("Spare", 1026)                   -- auto

Modbus.RegisterOutput("Card Scan", 1280)
Modbus.RegisterOutput("Card Out", 1281)
Modbus.RegisterDiscreteInput(name, address) / Modbus.RegisterCoilInput(name, address)

The same registration as Modbus.RegisterInput with the address space spelled out at the call site — RegisterDiscreteInput is always FC02, RegisterCoilInput always FC01.

Prefer these over RegisterInput. Its default is "auto", which cannot tell the two spaces apart on a PLC that answers both at one address — the failure mode described in the warning above. Naming the space is a decision the PLC's own I/O map already contains; leaving it to be probed is how a dashboard row ends up frozen.

Return: none.

Example:

Modbus.RegisterDiscreteInput("CardTaken", 1024)
Modbus.RegisterDiscreteInput("CardError", 1025)
Modbus.RegisterRegister(name, address, opts)

Declares a named, typed value living in a run of 16-bit registers, shown on the Dashboard's PLC Registers card. Modbus itself moves 16-bit words and nothing else — anything wider is a convention between the PLC program and whoever reads it, so every point states its type and its byte/word order explicitly.

opts fields (all optional except where noted):

  • type — "uint16", "int16", "uint32", "int32", "uint64", "int64", "float32", "float64", "string". Default "uint16". Common aliases (word, dword, real, dint…) are accepted.
  • endian — "ABCD" (default), "BADC", "CDAB", "DCBA"; "big"/"little" also work. See the table below.
  • length — required for "string", in BYTES (two per register).
  • source — "holding" (FC03, default) or "input" (FC04).
  • write — true to allow writing. Holding registers only.
  • unit — display-only label, e.g. "degC".

Byte and word order. For the 32-bit value 0x12345678 across two registers:

endianRegister 0Register 1Also called
ABCD0x12340x5678 big endian
BADC0x34120x7856 byte swap
CDAB0x56780x1234 word swap / mid-little
DCBA0x78560x3412 little endian

A float that reads as a wild number (2.7e+23) or a near-zero (1.4e-45) is almost always the wrong order, not bad data. The dashboard shows the underlying words in a Raw column next to each value precisely so you can compare against this table. Registering the same address twice under two orders shows both side by side.

FC03 vs FC04. Holding registers (FC03) are the read/write space, written with FC06 (single) or FC16 (multiple). Input registers (FC04) are read-only — Modbus defines no FC04 write frame at all, because that space models values the device produces. Passing write = true together with source = "input" raises an error at registration rather than failing later at the first write attempt.

Return: none. An unknown type, endian or source raises an error.

Example:

Modbus.RegisterRegister("Temperature", 4096,
    { type = "float32", endian = "CDAB", write = true, unit = "degC" })

Modbus.RegisterRegister("Device Tag", 4100,
    { type = "string", length = 16 })

Modbus.RegisterRegister("Live Current", 3000,
    { type = "float32", source = "input", unit = "A" })   -- FC04, read-only

See config/scripts/register_test.lua for one point per type.

Modbus.GetRegister(name) / Modbus.SetRegister(name, value)

Read and write a registered register point using its declared type and byte order, so a script never re-implements the word packing.

GetRegister returns the last polled value, or nil, error. SetRegister returns true, or false, error. Values that do not fit the target type are refused rather than truncated — a wrapped setpoint written to a machine is worse than a refused one.

Example:

local temp, err = Modbus.GetRegister("Temperature")
if temp then Log.Info("temp = " .. temp) else Log.Warning(err) end

local ok, err = Modbus.SetRegister("Setpoint", -120)
if not ok then Log.Warning("write refused: " .. err) end   -- e.g. "value 70000 does not fit uint16"
Modbus.ReadInputRegister(address) / Modbus.ReadInputRegisters(address, count)

Raw function-code 0x04 reads, returning undecoded 16-bit words (a single integer, or a table of them). Input registers are the read-only counterpart to holding registers — there is no write equivalent. Use Modbus.RegisterRegister above when you want a typed value instead of raw words.

Return: integer / table of integers, or nil on failure.

Example:

local words = Modbus.ReadInputRegisters(3000, 2)
if words then Log.Info(string.format("%04X %04X", words[1], words[2])) end

Card

Reads card UIDs submitted by external card reader clients over POST /api/card/input (see the Card Clients page and request/Request/cardInputRESTAPI.md) — an alternative to RFID hardware wired directly to this gateway. A single most-recent card is held in the cache until Card.Clear() is called.

Card.Available()

Reports whether a card is currently waiting in the cache.

Return: bool

Card.Get()

Reads the cached card without clearing it.

Return: a table — uid (string), position (integer), timestamp (integer, unix seconds) — or nil if none is cached.

Example:

local timeout, elapsed = 30000, 0
while elapsed < timeout do
  if Card.Available() then break end
  Sleep(100)
  elapsed = elapsed + 100
end

if Card.Available() then
  local card = Card.Get()
  Log.Info("Card UID: " .. card.uid .. " position " .. card.position)
  Card.Clear()
end
Card.Clear()

Empties the cache. Call this once a cached card has been consumed so the next Card.Available() correctly reports false until a new one arrives.

Return: none

Mq

RabbitMQ (AMQP 0-9-1) client — publish gateway events to a broker and consume commands from it. Configured on the Configuration page under RabbitMQ Broker; nothing here connects on its own, the client runs from gateway startup and reconnects on its own.

Two things worth knowing before using it:

  • Publishing is asynchronous. Mq.Publish() queues the message and returns; the broker gets it from the client's own thread. true means queued, not delivered. Call Mq.Flush() when a script must not move on until the message has actually left.
  • Received messages are acked on arrival, not when a script reads them, and are held in an inbox of mq.inbox_limit messages (oldest dropped when full). So a slow script loses messages rather than stalling the broker — and a message read with Mq.Get() is gone from the inbox for every other script.
Mq.IsConnected()

Whether the AMQP connection is up right now.

Return: bool

Mq.Publish(body [, routingKey [, exchange]])

Queues one persistent (delivery mode 2) message. Wraps body in the v1 envelope ({"id","ts","v":1,"body"}) when mq.envelope is on.

Parameters: routingKey defaults to mq.routing_key, exchange to mq.exchange.

Return: ok (bool), plus an error string when false — the broker being disabled, or the outbound queue being full.

Example:

local ok, err = Mq.Publish("card issued: " .. cardUid)
if not ok then
  Log.Error("Publish failed: " .. tostring(err))
end
Mq.PublishRaw(body [, routingKey [, exchange]])

Same, but never wraps: the body goes on the wire exactly as given, whatever mq.envelope says. For talking to a consumer that has its own payload format.

Return: ok (bool) [, error string]

Mq.Flush([timeoutMs])

Waits until the outbound queue is empty. Default timeout 2000 ms.

Return: bool — false means messages are still queued (broker unreachable, or slower than the timeout).

Mq.Available()

Whether at least one received message is waiting.

Return: bool

Mq.Get()

Takes the oldest received message out of the inbox.

Return: a table — body (the envelope's body, or the whole payload when envelopes are off), raw (payload as it arrived), id, ts, v, exchange, routing_key, redelivered, delivery_tag — or nil when the inbox is empty.

Example:

while Mq.Available() do
  local message = Mq.Get()
  Log.Info("MQ " .. message.routing_key .. ": " .. message.body)
end
Mq.Clear()

Discards every message waiting in the inbox.

Return: none

Mq.Pause(paused)

Cancels the consumer (true) or restarts it (false). Publishing is unaffected. Useful while a script is busy with a card and should not be handed commands.

Return: bool — whether the request was accepted.

Mq.Status()

Everything the dashboard shows, as one table: enabled, connected, consuming, paused, error (last AMQP/transport error, empty when healthy), the counters published, received, rejected (undecodable or oversized, dropped), dropped (refused because the outbound queue was full), overflowed (evicted from a full inbox), pending, available, and where it points: host, port, vhost, exchange, queue, routing_key. Never the password.

Return: table

zk_controller

Native module (not a global table) exposing the ZKTeco access-control controller connection, embedded directly in this process — see request/HSF_Machine_ZK_Controller_Lua_Integration.md and src/zk_controller/. No separate bridge process. local zk = require("zk_controller") to use it.

zk.connect(ip, port, timeout, password)

Synchronous, like a plain TCP connect attempt — does not retry itself.

Parameters: port default 4370, timeout (ms) default 2000, password default "".

Return: ok (boolean), err (string, only set when ok is false)

zk.disconnect()

Return: none

zk.isConnected()

Return: bool

zk.setAutoReconnect(enable)

Default true. Only ever applies after a connection that was up drops (heartbeat failure) — zk.connect() itself never retries.

Return: none

zk.startRTLog() / zk.stopRTLog()

Starts/stops the 500ms GetRTLog() poll that feeds zk.onCard()/ zk.onRawRTLog() below. No effect until connected.

Return: none

zk.onCard(function(event) ... end)

Registers the card-event callback (replaces any previously registered one). Fired for each real card swipe RTLog reports — door/alarm/password-fail records (which come through with CardData == "0") are filtered out first, same as the reference GUI app.

event fields: CardData (string), DoorID (integer), ReaderID (integer — which of the door's two readers produced the swipe: 0=entry, 1=exit, 2=none, per the SDK's GetRTLog buffer format), InOutStatus (integer — the same value under its raw RTLog field name), VerifyMode (integer), EventType (integer), Timestamp (integer, unix seconds, best-effort parse of RTLog's time string).

Example:

zk.onCard(function(event)
  Log.Info("Card " .. event.CardData .. " door " .. event.DoorID)
end)
zk.onRawRTLog(function(raw) ... end)

Debug callback: fired with the unfiltered GetRTLog() buffer on every non-empty poll, including door/alarm status and the "0"-card noise zk.onCard() filters out. Useful for confirming what the real controller actually sends before trusting any field mapping.

zk.onConnectionChanged(function(connected) ... end)

Fired only when the connection state actually changes (deduplicated, same guard as the original AppState) — never fires twice in a row with the same value.

zk.onAuxInput(function(input, shorted) ... end)

Fired when an auxiliary input changes: RTLog event 221 (shorted) or 220 (disconnected). This is the only way to read an input — the PullSDK has no read-input call, so an input nobody has triggered since start-up has no state at all.

Parameters of the callback: input (integer, the input number), shorted (boolean).

zk.lastError()

Return: string description of the last native PullSDK failure (connect/heartbeat/ reconnect), or an empty string if none yet.

Outputs: relays and auxiliary outputs. These wrap ControlDevice (SDK section 3.5). Two facts of the protocol shape all of them: outputs are write-only (nothing can ask a relay what it is doing), and the SDK's hold time is in whole seconds — 0 releases now, 1-60 holds for that many seconds, 255 latches until something releases it. Sub-second control is therefore latch-then-release, which is what zk.pulse() does for you.

zk.openDoor(door [, seconds])

Closes a door relay. seconds default 5.

Return: true, or nil plus the reason.

zk.auxOut(output [, seconds])

Same for an auxiliary output. seconds default 1.

zk.pulse(number [, durationMs] [, auxiliary])

Latches the output, waits durationMs (default 150), releases it. auxiliary defaults to true. Blocks for the duration on the calling script's thread, and costs two round trips to the panel.

zk.beep(number [, count] [, durationMs] [, gapMs] [, auxiliary])

There is no beeper command in the PullSDK — nothing in plcommpro.dll addresses the reader's own sounder, and no device parameter configures it. This pulses the named output count times, so what it sounds like depends on what is wired to that relay.

Example:

zk.beep(1, 5, 120, 120)   -- five short beeps on auxiliary output 1
zk.controlDevice(operationId, p1, p2, p3, p4 [, options])

The raw call, for an operation the wrappers do not cover. 1 = output (p1 door/aux number, p2 1=door 2=aux, p3 hold), 2 = cancel alarm, 3 = restart, 4 = enable/disable normal-open.

zk.cancelAlarm() / zk.restartDevice() / zk.setNormallyOpen(door, enable)

Return: true, or nil plus the reason.

zk.getParam(items) / zk.setParam(itemValues)

GetDeviceParam / SetDeviceParam. items is comma separated ("LockCount,AuxOutCount,AuxInCount,ReaderCount"); itemValues is "Field=Value,Field=Value". Values come back as strings — the parameter space mixes numbers, IP addresses and bit masks.

Return: table of name = value, or nil plus the reason.

zk.ioState()

Everything the controller has reported about its own I/O: doors (array of "OPEN" / "CLOSED" / "NO_SENSOR"), door_bytes, alarms, status_seen, status_time, inputs (map of input number to boolean), input_seen, and counts (locks, aux_out, aux_in, readers).

Door state arrives only in RTLog status records, which the panel sends when it has no events queued — so status_seen false means "not told yet", not "all closed".

zk.doorState(door) / zk.inputState(input)

Return: "OPEN"/"CLOSED"/"NO_SENSOR", and true (shorted) / false (open) respectively. Both answer nil when the panel has not reported that door or input yet — never a guess.

Db

SQLite for a script's own data. One connection per script, opened with Db.Open; the file is opened in WAL mode, so another process (or the gateway's own locker UI) can read it while this script writes. A relative path resolves against the gateway's config directory, beside config.db and logs.db.

Values are always bound, never pasted into the SQL. Every function takes an optional array of parameters for the ? placeholders. A statement whose parameter count does not match is refused rather than run — an unbound ? would silently become NULL and match nothing.

Db.Open(path)

Return: true, or nil plus the reason. Creates the file and any missing parent directory. Calling it again closes the previous connection.

local ok, err = Db.Open("smartlocker.db")
Db.Exec([[CREATE TABLE IF NOT EXISTS visits (
  id INTEGER PRIMARY KEY AUTOINCREMENT, card TEXT, at TEXT)]])
Db.Exec(sql [, params])

For statements that return no rows. Db.Execute is an alias.

Return: changes (integer), last_insert_id (integer), or nil plus the error message.

local changes, id = Db.Exec("INSERT INTO visits(card, at) VALUES(?, ?)", { uid, os.date("%F %T") })
Db.Query(sql [, params])

Return: array of row tables, or nil plus the error. A column that is SQL NULL is simply absent from the row table.

for _, row in ipairs(Db.Query("SELECT card, at FROM visits WHERE at > ?", { since }) or {}) do
  Log.Info(row.card .. " at " .. row.at)
end
Db.QueryOne(sql [, params]) / Db.Scalar(sql [, params])

The first row, and the first column of the first row. Both return nil with no second value when there is no such row (a normal answer), and nil plus a message when the statement failed.

Db.Begin() / Db.Commit() / Db.Rollback() / Db.InTransaction()

BEGIN IMMEDIATE, so two writers fail fast at the start rather than at commit. Nested Db.Begin() increments a depth counter and issues no SQL; a Db.Rollback() at any depth unwinds everything. Db.InTransaction() returns the depth.

Db.NULL

Binds SQL NULL. A Lua nil cannot: {1, nil, 3} is a one-element array as far as # is concerned, and the statement would be refused for having too few parameters.

Db.IsOpen() / Db.Path() / Db.Close() / Db.Quote(text)

Db.Quote is for identifiers and ORDER BY clauses only — values go through the parameter array.

Http

Lets a script answer HTTP requests. Crow's routing table is built when the gateway starts, so a script cannot add a URL of its own — instead everything under /api/app/ is forwarded to whichever running script registered that path. Up to three path segments below the prefix.

The handler runs on the script's own thread, at its next Sleep() — the only thread allowed to enter that VM. A web client is holding a connection open while it waits (5 second timeout, then 504), so a handler must return promptly and must not block on hardware.

Http.Register(method, path, handler)

method is "GET", "POST", … or "ANY". A path segment written <name> matches any single segment; the handler reads it back from request.path. Registering the same method and path again replaces the handler.

The handler receives one table: method, path (below the prefix), body, content_type, query (table), headers (Content-Type, API-Key, Accept, X-Requested-With).

The handler returns either status, body [, content_type], or a single string body (200), or nothing (204).

Http.Register("GET", "lockers", function(request)
  return 200, Json.encode(snapshot()), "application/json"
end)

Http.Register("POST", "lockers/<id>/unlock", function(request)
  local id = tonumber(request.path:match("lockers/(%d+)"))
  return unlock(id)
end)
Http.Unregister(method, path) / Http.Routes()

Http.Routes() returns this script's routes as "METHOD path" strings. GET /api/app on the gateway lists what every running script serves.

Runtime Variables

SetVariable(name, value)

Publishes a runtime variable visible on the Dashboard. value may be boolean, integer, float, or string.

Example:

SetVariable("DoorState", true)
GetVariable(name)

Return: the stored value, or nil if unset.

Event Handlers

Define any of these as global functions and the gateway calls them when the matching hardware event occurs — you don't call them yourself.

OnCitizenCardRead(cardJson)

Fired when the Citizen ID reader (Serial) produces a line that parses as a card. cardJson is the parsed fields as a JSON string (see the Citizen ID Card Format section).

OnRfidCardRead(uid)

Fired when the RFID reader reports a card UID. uid is that UID as a string.

OnPlcInputChanged(index, value)

Fired when a PLC input coil's value changes.

OnCardReceived(uid)

Fired when a card reader client posts to POST /api/card/input. Complements Card.Available()/Card.Get() for scripts that prefer an event handler over polling — the card is cached either way, so both styles can read it via Card.Get().

OnMqMessage(body)

Fired when the RabbitMQ client accepts a message. body is the same string Mq.Get().body would return. A wake-up only: the message is already in the inbox and already acked, so a handler that wants the routing key or envelope id calls Mq.Get() for the full table — and with several scripts running, whichever one calls Mq.Get() first takes it.

zk_controller (above) uses callback registration (zk.onCard(function(event) ... end)) instead of this named-global-function convention — see its own section for why (it's a require()'d module, not global bindings).

Delivery timing depends on how the script is structured. A script that just defines handlers and returns (the convention above assumes this) gets them called immediately, as soon as the event occurs. A script that instead polls in its own while true do ... end loop (e.g. calling Serial.Read() itself rather than defining OnCitizenCardRead) holds the engine's lock for as long as it runs, so events can't be delivered mid-loop by whatever background thread detected them — they're queued instead, and delivered the next time that script calls Sleep() or Serial.Read() (both drain the queue first). Mixing styles works fine — e.g. a script that polls Serial.Read() for citizen cards but still defines OnRfidCardRead for RFID scans — as long as it calls Sleep() or Serial.Read() regularly so queued events actually get delivered.

Utility

Sleep(milliseconds)

Blocks the script for the given duration — useful for pacing a Serial.Write followed by a Serial.Read, or a Tcp.Send followed by a Tcp.Receive.

Parameters: milliseconds (number)

Return: none

Example:

Serial.Open()
Serial.Write("PING")
Sleep(200)
local line = Serial.Read()

The whole Lua engine runs under a single lock (see the architecture note in CLAUDE.md), so a long Sleep call delays every other script event — OnCitizenCardRead, OnPlcInputChanged, the Log/Editor endpoints — until it returns. Fine for a short one-off test run from the Lua Editor; avoid long sleeps inside handlers that fire often.

Log

Log.Info(message) / Log.Warning(message) / Log.Error(message) / Log.Debug(message)

Writes to the gateway's Lua log category — console, the rotating log file, and the Runtime Log tab of the Log Viewer. This is the debugging channel: entries are free-form text, and the in-memory buffer the viewer reads is bounded, so old lines age out.

For records that must still be findable next month, use Log.Write below.

Log.Write(log_type, data [, level])

Writes a structured log entry into SQLite (config/logs.db), searchable on the Structured Logs tab by date range, type, level, script and keyword. This is the channel for business events — a card issued, a verification result — as opposed to debugging output.

Parameters: log_type (string, must be a type declared in config/log_definitions.json), data (flat table of field = value), level (optional string, default "INFO")

Return: true on success; false, message on failure.

The gateway validates data against the type's declaration before inserting, and rejects the whole write on:

  • an unknown log_type;
  • a field the type does not declare (this is what catches a misspelled field name, which would otherwise become an invisible column);
  • a missing field the type marks required;
  • a value that does not parse as the declared type (integer, number, boolean).

Nothing is written on a rejected call — the entry and its field values go in as one transaction, so a row can never appear with only some of its fields.

Example:

local ok, err = Log.Write("card_issue", {
    citizen_id    = citizen_id,
    employee_name = card.full_name,
    card_uid      = card_uid,
    machine_id    = Config.Get("system.machine_id"),
    result        = "success"
})
if not ok then
    Log.Error("could not record the issue: " .. tostring(err))
end

Add or change log types by editing config/log_definitions.json; the gateway loads it at startup. Scripts never create tables or run SQL — the three-table schema underneath stores arbitrary field sets without one table per log type.

Log.Types()

Lists the declared log types, so a script can check what it may write instead of finding out from a rejected Log.Write.

Return: array of tables: type (string), description (string), fields (array of { name, type, required })

Config

Read/write access to the gateway's own configuration — the same values the Configuration page edits and PATCH /api/config carries, addressed as "<section>.<key>". Scripts reach configuration only through these functions; there is deliberately no SQL surface in Lua.

Not to be confused with require("config"), the script-level config.lua table of workflow constants. Values that describe the gateway (machine id, PLC address, REST URL) belong here, where the Configuration page can edit them without touching a script.

Config.Get(key)

Parameters: key (string, e.g. "modbus.ip")

Return: the value as a string, number or boolean; nil, message when there is no such key.

Example:

local plc_ip     = Config.Get("modbus.ip")
local plc_port   = Config.Get("modbus.port")
local machine_id = Config.Get("system.machine_id")
local server_url = Config.Get("rest.server_url") -- nil: the key is "rest.url"
Config.Set(key, value)

Sets one value and writes the whole configuration back to SQLite immediately, so the change survives a restart.

Return: true, or false, message.

Fails rather than silently doing nothing when the key does not exist, or when the value is a different kind of thing than the field holds (a string where a number belongs). Both would otherwise look like success while the script read back the old value.

Sections whose modules re-read their settings each cycle (Modbus, RFID) pick a change up without a restart; others take effect on the next start.

Config.Exists(key)

Return: boolean.

Config.GetCategory(category)

Parameters: category (string, e.g. "modbus")

Return: a table of that section's keys; nil, message when there is no such section.

Example:

local plc = Config.GetCategory("modbus")
Log.Info("PLC at " .. plc.ip .. ":" .. tostring(plc.port))

Sections: system, web, rest, serial, serial2, modbus, rfid, zk, lua, logging, card_api.

config/scripts/config.lua is the worked example: installation-level settings (server URL, API key, PLC and ZK addresses, machine id) come from here, while the machine's mechanical timings, retry limits and coil addresses stay literal in that file. Each lookup carries the value it had before the migration as a fallback, and warns when it uses it — so a database that predates a key still runs unchanged.

Running Several Scripts

Scripts run independently: each has its own Lua state, its own thread and its own entry in the System Info tab (state, CPU, RAM, core, runtime id). Tick several in the Lua Editor's script tree and press Run Selected.

What that means when writing one:

  • Nothing is shared through globals. Two scripts have two separate global tables; pass data between them with SetVariable / GetVariable, which the whole gateway shares.
  • Every script gets every event. OnCitizenCardRead, OnRfidCardRead, OnCardReceived and OnPlcInputChanged are delivered to each running script that defines them — so if two scripts both handle card reads, both will act.
  • A failing script stops alone. It is marked ERROR, its error is recorded under the script_error log type, and the others keep running.
  • Hardware is shared, and not reserved. One serial port, one PLC connection. Two scripts writing to the LED display or driving the same coil will interleave; decide which script owns which device.
  • Starting a script that is already running does nothing — the UI reports "already running" rather than launching a second copy.

Error Codes

Native bindings never throw C++ exceptions into Lua. Failures are reported either as a returned nil / false value (see each function's Return above) or, for malformed arguments (wrong type, missing required parameter), as a Lua runtime error catchable with pcall and surfaced in the Lua Editor's Error Console.
